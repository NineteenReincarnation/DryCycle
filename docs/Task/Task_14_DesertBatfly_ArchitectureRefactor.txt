======================================================================
0. 任务定位
======================================================================

本任务不是新增玩法，也不是单纯“整理文件夹 / 批量重命名”。

本任务是在 Desert Batfly 已经拥有大量成熟行为之后进行的一次全项目架构收敛。

核心目标：

1. 完整回顾当前 Desert Batfly 源码、运行时、Hook、测试和 Debug；
2. 保持已经批准并实现的玩法与生态行为；
3. 修复本轮审查中已经确认或高度怀疑的隐性 Bug；
4. 收敛长期追加形成的 Bridge / Reflection / RuntimeDetour / Dynamic IL 技术债；
5. 建立统一 Frame Context、Room Context、Event、Behavior Arbitration 和普通 Flight execution；
6. 减少重复 Room scan / weapon scan / creature scan；
7. 让死亡、抓取、伤害等真实游戏事实只生成一次 Desert Batfly semantic event；
8. 将生产代码中的 Task09～Task13 开发历史术语退出运行时；
9. 将 C# 类型和文件的长前缀 DesertBatfly 收敛为 DB_；
10. 重新组织项目文件，让领域职责比历史实现方式更容易定位；
11. 重构测试，使测试保护行为契约和架构边界，而不是保护旧 Bridge；
12. 为 Corpse Ecology、繁殖以及未来更多大型生态机制提供可持续扩展基础。

本任务必须采用 Behavior-Preserving Refactor。

除明确列入本任务的 Bug 修复、性能收敛、可读性重构和架构替换外，禁止借本任务重新设计生物玩法。

2. 重构前必须保持的玩法基线
======================================================================

以下默认全部保持。

2.1 物种与外观
--------------------

- Desert Batfly 比原版 Batfly 更大；
- 颜色、花纹、spike、性别视觉差异保留；
- Personality 稳定 seed 保留；
- Male/Female 稳定 EntityID 结果保留；
- 性别不决定 Temperament / Nerve / Aggression 等人格轴。

2.2 被否决机制
--------------------

Task02 Emergent Social Roles 继续永久否决。

生产代码不得重新出现：

- Sentinel；
- Bully；
- Opportunist；
- permanent Leader；
- permanent Follower；
- SocialRole enum；
- role score；
- role locomotion controller。

个体差异继续来自 Personality + Experience + Environment。

2.3 Combat / Harass
--------------------

保持：

- Observe；
- Approach；
- Circle；
- FakeDive；
- Dive；
- Attach；
- Retaliation；
- AttackSlots；
- Grab struggle；
- SandSpit；
- 恶劣个体可骚扰轻型生物；
- PTSD / severe injury / hard survival 等 veto。

2.4 Rock
--------------------

Rock 可造成：

- stun；
- injury；
- wing damage；
- post-stun shock。

但单次 Rock Violence 不允许直接完成 live -> dead finishing transition。

2.5 Injury / Trauma
--------------------

保持：

- Injury；
- Wing injury；
- PhysicalCapability；
- PostStunShock；
- PredatorTrauma；
- PlayerTrauma；
- GrabMemory；
- recovery；
- Injury 对 flight capability 的影响。

2.6 Social
--------------------

保持：

- Conformity；
- SocialBond 单 persistent partner slot；
- bond 可非对称；
- Grief；
- Neutral Social Life；
- CompanionDrift；
- PassBy；
- SocialChase；
- GroupDrift；
- PositionNegotiation；
- RoostInvitation；
- ChainSocialization。

不建立完整 N×N social graph。

2.7 Vengeance
--------------------

保持 Extreme Vengeance 的设计语义。

- Vengeance 是否发生由现有 vengeance/fear 逻辑决定；
- Threat Signature 只改变“怎么打”，不决定“是否复仇”；
- Task09 Travel / HardSurvival 可暂停 Vengeance movement；
- 暂停不能清除 Vengeance memory。

2.8 Peach Lizard
--------------------

保持原生 Watcher Peach Lizard 管线：

- PreyTracker；
- Hunt；
- Tongue；
- Bite；
- ReturnPrey；
- 活体捕食；
- corpse scavenging。

不重写第二套 Peach AI。

2.9 Travel / Colony
--------------------

原 Task09 所批准内容全部保留：

- EmergencyRefuge；
- temporary displacement；
- ReturnHome；
- ColonyMigration；
- HomeColony；
- world route planning；
- LeaveRoom；
- abstract movement；
- route survivability；
- migration hysteresis/cooldown/history。

2.10 Threat Signature
--------------------

原 Task11 三层保持：

1. persistent Threat Signature memory；
2. current real cue；
3. acute event state。

继续禁止：

- 读取 Input；
- 读取 controller；
- 作弊预判下一次攻击；
- held item 本身直接训练 persistent memory。

2.11 Signals
--------------------

Signal 继续恰好六种：

- AlarmFlutter；
- DistressCall；
- RallySignal；
- RoostCall；
- HarassSignal；
- SafeSignal。

不得因为重构新增 WeatherCall / FogCall / ShelterCall 等类型。

2.12 Environment
--------------------

原 Task13 六 phase 保持：

1. Calm；
2. Advisory；
3. Preparation；
4. Sheltering；
5. Acute；
6. Recovery。

保持 DryCycle-only weather authority。

RoomSettings Fog / 普通 shader fog / palette effect 不能单独激活该生态系统。

保持：

- LightRain；
- Fog；
- DenseFog；
- HeavyRain；
- HeatWave；
- IntenseHeat；
- Sandstorm；
- DeathSandstorm；
- DeathRain。

HeavyRain 继续为非致死天气，最大项目 intensity 以实际 DryCycle 值为准，不假设 1.0。

2.13 Save compatibility
--------------------

现有 Desert Batfly persistent save schema 默认保持兼容。

重构 C# 类型名不得迫使旧存档改 tag。

3. 源码命名规范
======================================================================

3.1 DB_ 前缀
--------------------

Desert Batfly 生产源码的主要类型/文件逐步统一：

    DB_<完整职责名>

示例：

- DB_Creature；
- DB_State；
- DB_Personality；
- DB_Tuning；
- DB_Runtime；
- DB_FrameContext；
- DB_RoomContext；
- DB_EventHub；
- DB_BehaviorArbiter；
- DB_BehaviorProposal；
- DB_FlightMotor；
- DB_ThreatMemory；
- DB_SignalRuntime；
- DB_EnvironmentRuntime。

原则：

“前缀短，职责名完整。”

禁止二次不可读缩写：

- DB_EnvRt；
- DB_BhvArb；
- DB_TrvInt；
- DB_T11；
- DB_T13Env；
- DB_Helper2。

3.2 TaskXX 退出 runtime
--------------------

最终生产代码原则上不得存在：

- Task09Travel；
- Task10Social；
- Task11Threat；
- Task12SignalBridge；
- Task13Influence；
- DB_Task13...；
- task09OwnsFrame；
- task13HardSurvival。

替换为真正领域术语：

- TravelIntent；
- SocialInfluence；
- ThreatContext；
- ThreatMemory；
- SignalInfluence；
- EnvironmentInfluence；
- HardSurvival；
- PrimaryOwner。

Task 编号只允许长期存在于：

- docs/Task；
- docs/Discussion；
- Git history。

迁移期测试文件可暂时保留 TaskXX 名称，但最终测试也应按领域重组。

3.3 namespace
--------------------

DB_ 只压缩类型/文件前缀。

namespace 继续优先保持完整语义：

    DryCycle.Creatures.DesertBatfly

可根据领域建立：

    DryCycle.Creatures.DesertBatfly.Combat
    DryCycle.Creatures.DesertBatfly.Travel
    DryCycle.Creatures.DesertBatfly.Signals

不要求改成 DryCycle.DB。

3.4 外部身份保持 DesertBatfly
--------------------

源码 rename 不改变：

- CreatureTemplate.Type "DesertBatfly"；
- Sandbox unlock ID；
- save tag，例如 DCDesertBatflyV1；
- world/config tag；
- atlas/resource ID；
- 已发布第三方 compatibility ID。

内部 rename 和外部兼容严格分开。

4. 文件与目录可读性原则
======================================================================

4.1 不使用硬行数拆分
--------------------

本任务不以文件行数作为验收条件。

较大文件只触发职责审查。

审查问题：

1. 是否有多个独立修改理由？
2. 是否存在多个生命周期？
3. 是否存在可独立测试/演化子职责？
4. 是否有其他模块只需要其中一部分？
5. 修改一个功能时是否必须阅读大量无关代码？
6. 是否经常成为多个功能修改的冲突热点？
7. 是否暴露过大 API surface？

即使 1200 行，只要高度内聚，也可以合理保留。

即使 400 行，如果同时承担感知、战斗、天气、移动和事件，也必须拆。

======================================================================
5. 当前项目审查确认的问题清单
======================================================================

以下问题必须在 Task14 中逐项关闭或给出明确保留理由。

5.1 P0 — 没有真实 Behavior Owner
--------------------

当前 UpdateAI 依赖：

- 固定调用顺序；
- return；
- CancelForPriority；
- frame stamp；
- localGoal 覆盖；
- private detour。

目标：建立真实 DB_BehaviorArbiter，并记录 PrimaryOwner。

5.2 P0 — Injury Recovery Dijkstra 语义不一致
--------------------

原版 FlyAI/Home-Hive 路径使用：

    ProgressLocalGoalAlongDijkstraMap(localGoal, map)

现有 Injury Recovery 路径存在以 body current position 作为推进输入的实现。

潜在后果：

- short-step jitter；
- goal 在身体附近反复重建；
- 狭窄地形来回切换；
- 与 native FlyAI path progression 竞争。

要求：

- 修复 Dijkstra input semantics；
- Injury recovery 只提交 Recovery proposal；
- Injury 对 flight 的影响通过 modifier 进入统一执行。

5.3 P0 — Travel realized 同帧潜在重复推进
--------------------

当前 Rain/Flee hook 与 AI update 都可能进入 TryDriveRealized。

已有 LastObservedFrame 只保护部分逻辑。

要求：

每只 DB_Creature 每个 frame/game clock：

- Travel realized tick 最多一次；
- DepartureDelay 最多递减一次；
- ReplanCooldown 最多递减一次；
- SameRoomTravelTicks 最多推进一次；
- LeaveRoom 不得重复请求。

5.4 P0 — 死亡 attribution 分裂
--------------------

当前死亡可能被：

- Creature/Intimidation；
- Threat Runtime；
- Colony Hooks；

分别推断 killer/cause。

要求：统一 DB_MortalityEvent。

5.5 P0 — Capture/Peach Tongue 多 Hook
--------------------

当前 Core、Peach integration、Signal integration 都可能观察同一 Tongue attach transition。

要求：

- detection once；
- publish DB_CaptureEvent once；
- Fear/Signals/Injury/Social/Threat 分别消费；
- 不依赖“多次调用但下游碰巧去重”。

5.6 P0 — CorpseWarning 生命周期残留
--------------------

现有短期 UpdatableAndDeletable warning 不被 Reset/Disable 集中拥有。

要求：

- transient ecology object 必须有 registry/lifecycle owner；
- Disable / Room teardown 可完整清理；
- 优先迁入 Room event/evidence state，而非每次死亡建立自治 runtime object。

5.7 P1 — Environment 临时改写 Thirst
--------------------

禁止继续：

    save Thirst
    write fake decision Thirst
    call old AI
    restore Thirst

建立 DB_CombatMotivation，显式组合：

- HydrationDrive；
- HeatAgitation；
- GriefAnger；
- RetaliationDrive；
- SocialHarassDrive；
- EnvironmentalDefenseDrive；
- InjuryScale；
- ThermalExhaustion；
- PTSD/HardSurvival veto。

5.8 P1 — 重复 weapon perception
--------------------

旧 AI ScanWeapons、Threat cache、DenseFog close fallback 不应各自完整扫描。

要求：统一 DB_WeaponPerception / Room weapon observation。

5.9 P1 — 旧 social harass contagion 与 Signal 并存
--------------------

旧 FindSocialHarassTarget 直接读取邻居 Target/Mode 的传播路径，应被正式 HarassSignal 取代。

不保留两套 social contagion。

5.10 P1 — Signal 参数复制
--------------------

VisualRadius / AcousticRadius 由 DB_SignalDefinition 唯一拥有。

Environment/Fog 只输出 visibility modifier。

5.11 P1 — Room runtime 不够 lazy
--------------------

没有 Desert Batfly 的普通 realized room 不应因为 Room.Update 自动建立完整 shelter/signal/ecology runtime。

5.12 P1 — Tests 锁死 Bridge
--------------------

MethodCallOffset / xxxBridge exists / xxxHook exists 等只能作为迁移期 architecture lock。

最终必须改为 contract test。

5.13 P1 — Observatory ControlOwner 目前是事后猜测
--------------------

重构后 Debug 应读取 Arbiter 的真实 PrimaryOwner、winner 和 reject reason。

5.14 P1 — AttackSlots 仍存在 room-wide counting pressure
--------------------

可以保留现有 bounded scan，也可以迁入 RoomContext/AttackSlotRegistry。

如果优化：

- target identity 必须稳定；
- death/cancel/room change 释放；
- 不引入 persistent complex registry；
- AttackSlots 语义不得变化。

6. 新核心：DB_FrameContext
======================================================================

DB_FrameContext 表示“当前帧已知事实”，不是行为结果。

至少包含：

Identity:
- DB_Creature；
- EntityID；
- Tick / frame；
- Room。

Physical:
- Position；
- Velocity；
- Conscious；
- Dead；
- Restrained；
- InShortcut；
- InHive；
- native Fly movement mode；
- native FlyAI behavior。

Individual:
- Personality；
- PhysicalCapability；
- Injury；
- PostStunShock；
- real Thirst；
- Trauma；
- Grief；
- Bond summary。

Perception:
- visible players；
- predator candidates；
- weapon observations；
- incoming projectile cue；
- visibility factor。

Domain influences:
- Travel summary；
- Signal influence；
- Environment influence；
- Threat summary；
- Social eligibility；
- Roost summary。

Rules:
- ImmediateDanger；
- HardSurvival；
- CombatAllowed；
- SocialAllowed；
- CrossRoomOwned；
- SpecialPhysicsOwner。

FrameContext 不存档。

模块不得为了拿信息去 Reflection 兄弟模块 private field。


======================================================================
7. 新核心：DB_RoomContext
======================================================================

目标：让多个模块共享真实 Room observation，但仍保持各领域 state ownership。

推荐共享：

- active DB bats；
- players；
- thrown weapons；
- predator candidates；
- room clock/context；
- low-level visibility observations；
- optional roosting view。

不要求把所有领域状态都塞进一个巨型 RoomContext。

以下仍由领域自己拥有：

- Signal packet internals；
- Social reservation；
- Environment anchor scoring semantics；
- Colony persistent state；
- TravelIntent；
- Threat persistent memory。

DB_RoomContext 是共享 observation/access layer，不是 God Object。


======================================================================
8. 新核心：DB_EventHub
======================================================================

至少统一：

- DB_DamageEvent；
- DB_StunEvent；
- DB_CaptureEvent；
- DB_ReleaseEvent；
- DB_MortalityEvent；
- DB_ConsumeEvent；
- DB_RoomChangedEvent；
- DB_BurrowEvent；
- DB_EmergeEvent；
- DB_VengeanceArmedEvent。

要求：

- 一个真实 semantic event 有唯一 sequence/id；
- 一个 subscriber 对同 sequence 最多处理一次；
- 外部 Hook 重复观察不得造成重复训练；
- event source / tick / position 可 Debug；
- 时间窗用于 attribution，不用于替代 exactly-once dispatch。


======================================================================
9. 统一 DB_MortalityEvent
======================================================================

推荐字段：

- Victim；
- Tick；
- Position；
- Cause；
- Instigator；
- SourceObject；
- DamageType；
- WasCaptured；
- WasConsumed；
- WasProjectile；
- WasCounterKill；
- ThreatEvidence；
- AttributionConfidence；
- DebugReason。

规则：

- live -> dead 只发布一次；
- Rock non-finishing rule 保留；
- environmental death 可 Instigator=null；
- 当前被抓住不自动等于 grabber 是 killer；
- Fear/Vengeance、Threat、Grief、Signals、Colony 全部使用同一 attribution；
- 后续 Corpse Ecology 也必须消费此事件，而不是再 Hook 一套 Death attribution。


======================================================================
10. 统一 DB_CaptureEvent
======================================================================

Consumers：

- Signals；

======================================================================
11. DB_BehaviorProposal / DB_BehaviorArbiter
======================================================================

11.1 Proposal
--------------------

推荐字段：

- Owner；
- Priority；
- BehaviorKind；
- Goal；
- NominalSpeed；
- DesiredNativeBehavior；
- DesiredDijkstraMap；
- RequestBurrow；
- SuppressCombat；
- SuppressSocial；
- PreserveGoal；
- Commitment；
- Reason。

Proposal 不直接写普通 locomotion velocity。

11.2 Priority semantic order
--------------------

总体保持：

1. death / unconscious / destroyed；
2. special restraint / grabbed / shortcut / emergence；
3. immediate physical danger / escape；
4. severe Injury / InjuryRecovery；
5. active realized Travel；
6. Environment Acute HardSurvival；
7. PTSD / direct threat response；
8. Extreme Vengeance；
9. Environment Preparation/Sheltering local survival；
10. immediate projectile evade modifier；
11. formal combat / retaliation / harass；
12. roost / chain；
13. neutral social；
14. ordinary species idle/swarm；
15. vanilla fallback。

注意：

- TravelIntent 存在但 suspended 时不自动获得 owner；
- HardSurvival 暂停 Vengeance 不清状态；
- Signals 永远不是 locomotion owner；
- Threat memory 永远不是 locomotion owner；
- Fog uncertainty 是 modifier，不是独立 owner。

11.3 Result
--------------------

每帧只输出一个 ResolvedBehavior：

- PrimaryOwner；
- WinningProposal；
- final goal；
- final speed；
- final native behavior；
- modifiers；
- rejected proposals + reason（debug only）。

27. Performance
======================================================================

目标：20～30 realized DB_Creature 单房时不因 Task14 增加明显架构性 spike。

禁止：

- 每 bat 每 frame 全 room physicalObjects scan；
- 每 bat 每 frame 全 DB population scan；
- 每 bat 每 frame terrain scan；
- 多个系统重复 weapon scan；
- Debug 关闭仍大量分配字符串；
- 无关 room 自动建 shelter terrain cache。

推荐按需要使用 bounded cadence：

- active bat/player list：事件 + 10～20 tick refresh；
- weapon observation：8～12 tick + urgent direct cue；
- social candidates：约 20 tick；
- environment/weather：约 20 tick；
- flock snapshot：约 30 tick；
- shelter anchors：build once/invalidate；
- individual expensive decisions：stagger。

这些数值是初始性能预算，不是绝对 API；实机 profiling 可调整。

39. 本任务真正的成功标准
======================================================================

Task14 完成后，新增一个 Desert Batfly 大型功能时，理想接入方式应是：

1. 找到清晰领域目录；
2. 读取 DB_FrameContext / DB_RoomContext 或明确领域 API；
3. 如果是事实，发布/消费 semantic event；
4. 如果是信息，输出 influence/context；
5. 如果需要普通移动，提交 BehaviorProposal；
6. Arbiter 决定是否拥有当前帧；
7. FlightMotor/native Fly 执行；
8. Observatory 能直接显示 owner、proposal、event；
9. 不需要 Reflection 兄弟模块 private state；
10. 不需要新增 *TaskXXBridge；
11. 不需要为了接入新功能再复制一套 Room scan；
12. 不需要把所有新代码重新塞回一个巨型 AI 文件。

项目可读性的成功标准不是“所有文件都很短”。

真正标准是：

- 文件和目录能快速告诉开发者职责；
- 修改一个领域无需理解大量无关系统；
- 状态 owner 明确；
- 事件 authority 明确；
- 普通移动 owner 明确；
- 依赖方向明确；
- 生命周期明确；
- 性能成本有界；
- 测试保护真实行为；
- 外部兼容稳定；
- 项目继续增长后仍能安全扩展。
