======================================================================
0. 任务定位
======================================================================

本任务不是一个新玩法任务，也不是一次单纯的“整理文件夹 / 批量重命名”。

本任务的目标是：

1. 回顾并重构当前完整 Desert Batfly 项目；
2. 保持已经批准并实现的生态、AI、社交、天气、战斗和存档行为；
3. 收敛 Task09～Task13 连续追加后形成的跨模块 Hook / Bridge / Reflection / RuntimeDetour 技术债；
4. 建立唯一、明确、可观测的行为控制权、事件流、感知流和普通飞行执行流；
5. 去除重复扫描、重复感知、重复事件解释和不必要 Room Runtime；
6. 修复在本轮全项目审查中确认或高度怀疑的隐性 Bug；
7. 重构测试，使测试保护“行为契约”而不是保护历史 Bridge 实现；
8. 重新整理 Desert Batfly 源码目录和文件职责，提高项目长期可读性；
9. 将生产源码中的长前缀 DesertBatfly 统一收敛为 DB_ 前缀；
10. 将 Task09 / Task10 / Task11 / Task12 / Task13 等开发阶段编号从生产运行时代码中移除；
11. 为后续 Corpse Ecology、繁殖和其他大型生态任务提供稳定扩展基础。

本任务完成后，Desert Batfly 应从：

“多个成熟功能模块通过补丁互相协调”

进入：

“多个成熟功能模块通过正式 Runtime / Event / Context / Arbiter / Perception 协议协作”。

本任务必须执行“行为保持型重构”。
除任务书明确列出的 Bug 修复、结构优化和命名迁移外，不得借重构之名改变已批准玩法。


======================================================================
1. 为什么现在必须重构
======================================================================

Desert Batfly 当前已经包含：

- Creature / State / Personality / Graphics；
- Injury / Shock / Trauma / Grab Memory；
- Harass / Observe / FakeDive / Dive / Attach / Retaliation；
- SandSpit；
- Roost / Fly Chain / platform underside；
- SocialBond / Sex / Grief；
- Extreme Vengeance；
- Peach Lizard 捕食；
- Colony Migration / Refuge / ReturnHome / World Route；
- Neutral Social Life；
- Threat Signature Memory / Current Cue / Tactics；
- Observable Social Signal Network；
- Environmental Activity / Shelter / Weather Ecology；
- Observatory / Debug Trace；
- Warp / Sandbox / Watcher compatibility；
- 一套较大的静态、反射式和行为数学回归测试。

这些功能单独看多数已经成熟。
当前主要问题不是“功能不够”，而是后续任务为了尽量不侵入前一任务，逐渐形成：

- 一个模块 Detour 另一个模块的 private method；
- Reflection 读取另一个模块 private field；
- DynamicMethod / ILGenerator 作为内部接口；
- frame stamp 阻止另一个模块在某一帧运行；
- 保存/恢复 localGoal 来保护优先级；
- 临时修改持久状态再恢复以影响另一个系统的决策；
- 同一 Room 存在多套低频扫描器；
- 同一物理/死亡/抓取事件被多个 Hook 分别解释；
- 同一个概念在不同模块复制参数；
- Observatory 只能“猜测”控制权，而不是读取真实控制权；
- 顶层文件不断增加，文件名过长，核心职责难以快速定位；
- Task 编号逐渐渗入运行时术语，开发历史与软件架构混在一起。

继续直接新增大型生态功能，会进一步增加 Bridge 数量和文件数量。
因此本任务优先于后续 Corpse Ecology 等大型功能。

2. 总体硬原则
======================================================================

2.1 行为保持
--------------------

重构前已经批准的行为默认必须保持。

特别包括：

- Desert Batfly 体型、外观、花纹、刺、性别差异；
- Personality 稳定随机分布；
- Emergent Social Roles 永久否决；
- 不得重新出现 Sentinel / Bully / Opportunist / permanent Leader / permanent Follower / Role enum；
- Rocks 可伤害、可重度眩晕，但单次 Rock Violence 不能直接完成 live -> dead；
- SandSpit；
- Grab struggle；
- Injury / Wing damage / PostStunShock；
- PTSD / GrabMemory / PredatorTrauma；
- SocialBond 单槽、非 N×N 图；
- Grief；
- Extreme Vengeance；
- Peach Lizard 原生 PreyTracker/Hunt/Tongue/Bite/ReturnPrey 管线；
- 跨房生态和路线所有权；
- Neutral Social Life；
- Threat Signature 三层语义；
- 恰好六种 Observable Signal；
- 六阶段 Environment behavior；
- DryCycle-only weather authority；
- HeavyRain / DeathRain / Fog / DenseFog / Heat / Sandstorm 已批准语义；
- 现有 DesertBatflyState 存档兼容。

2.2 不推倒重写
--------------------

不得把已经工作的 Colony / Travel / Social / Threat / Signals / Environment 系统全部重新实现。

优先策略必须是：

- 保留纯数学；
- 保留已验证决策规则；
- 保留 bounded cache；
- 保留现有存档格式；
- 替换模块之间的连接方式；
- 删除被新正式 API 取代的旧 Bridge / Detour / dead code。

2.3 内部零 Reflection 原则
--------------------

完成本任务后，Desert Batfly 自己的模块之间不得依赖：

- Reflection 获取另一个 DB_ 模块的 private field；
- RuntimeDetour 挂另一个 DB_ 模块的 private method；
- DynamicMethod / ILGenerator 适配另一个 DB_ 模块；
- 字符串方法名作为内部功能契约。

Reflection / Harmony / RuntimeDetour 只允许出现在真正的外部兼容/游戏 Hook 边界：

- Rain World；
- Watcher；
- Warp；
- 未来第三方 Mod compatibility。

2.4 单一普通飞行所有权
--------------------

普通飞行期间，任何时刻只能存在一个 Primary Movement Owner。

Environment、Social、Threat、Vengeance、Injury 等模块不得各自成为一套普通飞行控制器。

特殊物理状态可明确绕过普通 FlightMotor：

- Emergence；
- Attach；
- Interfere；
- 被抓/约束；
- 碰撞瞬时反冲；
- 攻击瞬时 impulse；
- SandBurst cosmetic；
- 原生 Shortcut/Burrow/Chain 的物理所有权。

2.5 跨房所有权不得削弱
--------------------

现有 Travel / Colony 系统继续独占：

- EmergencyRefuge destination；
- ReturnHome route；
- ColonyMigration；
- HomeColony change；
- World route planning；
- LeaveRoom；
- abstract movement；
- cross-room weather refuge；
- migration memory/stress/history。

Environment / Social / Threat / Signals 不得通过本次重构取得跨房移动权。

2.6 Task 编号退出生产代码
--------------------

Task09、Task10、Task11、Task12、Task13、Task14 是开发文档编号，不是软件架构名称。

最终生产代码中不得出现以下类型的长期命名：

- Task09Travel；
- Task10Social；
- Task11Threat；
- Task12SignalBridge；
- Task13Influence；
- DB_Task13...；
- task09OwnsFrame；
- task12Context；
- task13HardSurvival。

这些应改为真正的领域名称：

- TravelIntent；
- SocialInfluence / SocialProposal；
- ThreatContext / ThreatMemory；
- SignalPacket / SignalInfluence；
- EnvironmentContext / EnvironmentInfluence；
- HardSurvival；
- PrimaryOwner。

Task 编号只允许存在于：

1. docs/Task/ 正式任务书；
2. docs/Discussion/ 历史讨论记录；
3. 重构迁移期用于标识“旧任务行为契约”的临时测试文件名；
4. Git 历史。

R6 完成后，src/Creatures/DesertBatfly/ 下生产源码原则上必须达到 TaskXX 命名归零。

2.7 DB_ 源码前缀
--------------------

为提高项目文件和类型可读性，DesertBatfly 源码层统一采用：

    DB_

作为模块前缀。

核心规则：

- 长前缀 DesertBatfly 在生产 C# 类型名和文件名中逐步退出；
- DB_ 后使用完整、清晰的职责名；
- 不允许为了继续缩短而制造不可读二次缩写。

推荐：

- DB_Creature；
- DB_State；
- DB_Personality；
- DB_Tuning；
- DB_Runtime；
- DB_FrameContext；
- DB_RoomContext；
- DB_BehaviorArbiter；
- DB_BehaviorProposal；
- DB_FlightMotor；
- DB_EventHub；
- DB_EnvironmentInfluence；
- DB_ThreatMemory；
- DB_SignalRuntime。

禁止：

- DB_EnvInf；
- DB_BhvArb；
- DB_RtCtx；
- DB_T11；
- DB_T13Env；
- DB_Mgr1 / DB_Helper2。

原则：

“前缀短，职责名完整”。

2.8 外部身份字符串不得因 DB_ 重命名而改变
--------------------

DB_ 只属于源码可读性重构。

以下对游戏、存档、资源或第三方兼容可见的稳定身份默认保持不变：

- CreatureTemplate.Type 字符串 "DesertBatfly"；
- Sandbox unlock string "DesertBatfly"；
- 已存在的 save schema/tag，例如 DCDesertBatflyV1；
- 已发布资源 key / atlas key / external config key；
- World 文件中已经定义的物种/群落语义字符串；
- 第三方兼容层依赖的稳定外部 ID。

不得因为 C# 类型改成 DB_State，就把旧存档 tag 随意改成 DB_StateV1。

源码内部重命名和外部数据兼容必须严格分开。


======================================================================
3. 本轮审查已确认的架构问题与隐性风险
======================================================================

以下问题必须在重构过程中逐项关闭。

3.1 P0：没有真实 Behavior Owner
--------------------

当前 UpdateAI 主要依靠固定调用顺序、return、CancelForPriority、frame stamp、保存/恢复 localGoal 维护优先级。

目标：建立真实 DB_BehaviorArbiter，运行时明确记录当前 PrimaryOwner。

3.2 P0：Injury Recovery Dijkstra 语义不一致
--------------------

原版 FlyAI / Home-Hive 路径使用：

    ProgressLocalGoalAlongDijkstraMap(localGoal, map)

当前重伤恢复路径曾使用 body current position 作为推进输入。

这可能造成：

- 重伤返 Hive 短步抖动；
- localGoal 反复靠近身体；
- 狭窄地形方向切换；
- 与原生路径推进互相竞争。

要求：

- 修正 Dijkstra 推进语义；
- Injury 决策不再直接成为第二套普通飞行控制器；
- Injury 仅提交 recovery proposal + flight capability modifier。

3.3 P0：Travel realized drive 潜在同帧重复调用
--------------------

当前 FleeFromRainUpdate 与 UpdateAI 都可能进入 TryDriveRealized。
已有部分 LastObservedFrame 保护，但不是所有 countdown/cooldown 操作都位于同一 guard 后。

要求：

- 每只 DB_Creature 每个 frame/game clock，TravelRuntime realized tick 最多执行一次；
- Rain hook 不允许再次完整推进同一 TravelIntent；
- 增加自动回归验证 DepartureDelay / ReplanCooldown 单帧最多递减一次。

3.4 P0：死亡归因分裂
--------------------

当前 live -> dead 可能分别被：

- Creature.Die / Intimidation；
- Threat Runtime Creature.Die；
- Hooks.CreatureDie / ColonyRuntime；

使用不同 killer/cause/time-window 解释。

要求：建立统一 DB_MortalityEvent。

所有以下模块必须消费同一死亡事实：

- Fear / Intimidation；
- Threat Signature；
- SocialBond / Grief；
- Signals；
- ColonyRuntime；
- Observatory；
- 后续 Corpse Ecology。

3.5 P0：抓取/Peach Tongue 事件存在多 Hook 路径
--------------------

当前 Core Hooks、Peach integration、Signal integration 均可能观察 LizardTongue.Update。
现有代码主要依赖下游时间窗去重。

要求：

- Peach/other capture 只检测一次；
- 生成统一 DB_CaptureEvent；
- Fear/Signals/Injury/Social/Threat 各自订阅；
- 不再靠多 handler 重复 Threatened 后由幂等兜底。

3.6 P0：CorpseWarning 生命周期残留
--------------------

Intimidation 的短期 Room object 在 Reset/Disable 时缺少集中销毁所有权。

要求：

- 不再生成无法被 runtime 集中追踪的 DB ecology Updatable；
- 若保留 transient object，必须登记到 DB_RoomContext / transient registry 并在 Disable/Room teardown 清理；
- 优先把 death-site warning 状态迁入 Room ecology/event runtime，而不是每次死亡 new 自治 Update object。

3.7 P1：Environment 临时改写 Thirst 传递攻击动机
--------------------

当前环境 integration 曾通过：

    save Thirst
    set decision Thirst
    ScanCreatures()
    restore Thirst

把 HeatAgitation/Harass multiplier 注入旧 AI。

要求：删除该机制。

新增明确 DB_CombatMotivation：

- HydrationDrive；
- HeatAgitation；
- GriefAnger；
- RetaliationDrive；
- SocialHarassDrive；
- EnvironmentalDefenseDrive；
- PhysicalCapability / Exhaustion modifier。

任何决策不得临时篡改持久 CreatureState 作为函数参数。

3.8 P1：旧感知与 Threat 感知重复
--------------------

当前旧 AI ScanWeapons、Threat thrown weapon cache、DenseFog fallback 可能分别扫描 weapons。

要求：

- 建立统一 DB_WeaponPerception / Room weapon cache；
- 普通 AI / Threat / Fog fallback 读取同一真实 weapon observation；
- close projectile safety 保留；
- 不读取玩家输入或隐藏意图。

3.9 P1：旧 social harass 逻辑被 Signals detour 遮盖
--------------------

旧 FindSocialHarassTarget 通过读取邻居 AI.Target / Mode 实现 contagion；
正式 HarassSignal 已经批准用于传播该类信息。

要求：

- 删除被正式 Signal 网络取代的旧邻居私有状态窥探路径；
- 不保留两套同时可用的 harass contagion。

3.10 P1：Signal / Environment 参数复制
--------------------

VisualRadius / AcousticRadius 等 signal 参数不得在 Fog integration 再复制一套。

要求：

- DB_SignalDefinition 成为唯一 signal range authority；
- Environment 只提供 VisibilityMultiplier / Perception modifier；
- 调整 signal 参数时无需同步修改 Fog 常量。

3.11 P1：Room runtime 不够惰性
--------------------

当前部分 Room.Update 路径会对没有 Desert Batfly 的 realized room 创建 Signal/Environment/Refuge 数据。

要求：统一 DB_RoomContext 激活条件。

仅在以下情况之一成立时建立/更新昂贵 room state：

- 房间存在 realized DB_Creature；
- 房间属于 Desert colony/home；
- Travel/Colony 明确查询该房间生态；
- Observatory 明确请求该房间 debug；
- 某个真实 DB event 临时需要。

不得让普通地图房间仅因 Room.Update 就扫描 shelter terrain。

3.12 P1：测试保护了 Bridge，而非行为
--------------------

现有部分测试通过：

- MethodCallOffset；
- xxxBridge 必须存在；
- xxxHook 必须存在；
- MarkTravelOwnedFrame 必须被调用；

保护当前实现。

重构时必须改为测试：

- priority contract；
- ownership contract；
- event exactly-once；
- save compatibility；
- behavior math；
- forbidden side effects；
- no internal reflection；
- no duplicate travel tick；
- naming/readability boundary。

3.13 P1：生产文件命名过长且职责定位困难
--------------------

当前大量文件以 DesertBatfly 开头，文件名在 IDE 中高度同质化。
例如：

- DesertBatflyEnvironmentalIntegration.cs；
- DesertBatflyEnvironmentalSurvivalBridge.cs；
- DesertBatflyThreatVengeanceBridge.cs；
- DesertBatflySignalDirectWitnessBridge.cs。

问题不是单纯字符数，而是：

- IDE tab / search result 前半段全部相同；
- 真正职责词出现在文件名末尾；
- Bridge 命名反映的是历史接线方式，不是领域职责；
- 同目录大量文件难以快速形成心智地图。

要求：

- 迁移到领域目录；
- 类型/文件改为 DB_ 前缀；
- 文件名把核心职责放在 DB_ 后立即表达；
- 删除完成使命的 Bridge 文件。


======================================================================
4. 源码命名与文件可读性规范
======================================================================

本节为 Task14 硬规范，不是可选风格建议。

4.1 命名基本格式
--------------------

Desert Batfly 生产代码主类型统一：

    DB_<完整职责名>

示例：

    DB_Creature
    DB_State
    DB_Personality
    DB_Tuning
    DB_Runtime
    DB_FrameContext
    DB_RoomContext
    DB_BehaviorArbiter
    DB_BehaviorProposal
    DB_FlightMotor
    DB_EventHub
    DB_ThreatMemory
    DB_SignalRuntime
    DB_EnvironmentInfluence

对应文件名：

    DB_Creature.cs
    DB_State.cs
    DB_Personality.cs
    ...

原则上“主类型名 = 文件名”。

4.2 不改变 namespace 语义
--------------------

DB_ 是类型/文件前缀，不要求把 namespace 改成难读的缩写。

推荐继续保留语义明确的 namespace，例如：

    DryCycle.Creatures.DesertBatfly
    DryCycle.Creatures.DesertBatfly.Runtime
    DryCycle.Creatures.DesertBatfly.Behavior.Combat
    DryCycle.Creatures.DesertBatfly.Ecology.Environment

不要把 namespace 改成：

    DryCycle.Creatures.DB
    DryCycle.DB

除非后续整个项目有统一 namespace 迁移方案。

4.3 文件夹使用领域名，不使用 Task 编号
--------------------

允许：

- Core；
- Runtime；
- Perception；
- Behavior；
- Ecology；
- Presentation；
- Integration；
- Debug；
- Combat；
- Injury；
- Social；
- Threat；
- Signals；
- Environment；
- Colony；
- Travel。

禁止：

- Task09/；
- Task10/；
- Task11/；
- Task13/；
- PhaseR3/；
- OldBridge/；
- TempNew/。

4.4 不建立泛化垃圾目录
--------------------

禁止通过以下目录掩盖职责不清：

- Utils/；
- Helpers/；
- Misc/；
- CommonStuff/；
- Managers/。

如果一个 helper 只服务 Travel，就放 Travel。
如果只服务 Signals，就放 Signals。
真正跨领域的基础设施应进入 Runtime / Perception / Event，并有明确职责名。

4.5 一文件一主职责
--------------------

默认一个文件只包含一个主要顶层类型/主要职责。

允许同文件出现：

- 与主类型强绑定的小型 readonly struct；
- 小型 enum；
- private nested state；
- 不值得独立公开的纯数据载体。

禁止为了减少文件数把：

- EventHub；
- FrameContext；
- Arbiter；
- FlightMotor；
- Combat state machine；

重新塞进一个巨型 DB_Runtime.cs。

4.6 文件长度可读性预算
--------------------

这是软约束，但必须主动审查：

- 约 0～500 行：正常；
- 约 500～800 行：可以接受，但应确认职责是否仍单一；
- 超过约 800 行：必须检查是否可按职责拆分；
- 超过约 1200 行：生产手写代码原则上应拆分，除非存在非常明确且记录在案的理由。

禁止机械地为了“每文件 300 行”把一个状态机切成几十个无意义碎片。
目标是提高导航和职责清晰度，不是追求文件数量指标。

4.7 方法可读性
--------------------

高复杂度方法应优先拆成：

- Gather / Sample；
- Evaluate；
- BuildProposal；
- Resolve；
- Apply；
- Publish；

等明确阶段。

一个方法同时做：

“扫描全房间 + 修改状态 + 选择目标 + 改 localGoal + 发信号 + 写 debug”

应被视为重构目标。

4.8 类型命名表达领域，不表达历史补丁
--------------------

应逐步删除以下生产命名模式：

- *Bridge；
- *Task09Bridge；
- *Task13Bridge；
- *Patch（若不是外部 patch）；
- *Hook（若不是 Rain World 外部 hook）；
- *Compatibility（若实际只是内部模块接线）。

替代为实际职责：

- Policy；
- Runtime；
- Perception；
- Influence；
- Proposal；
- Adapter；
- Registry；
- Event；
- State；
- Resolver。

外部边界文件仍可使用：

- Hook；
- Adapter；
- Integration；
- Compatibility。

4.9 DB_ 不重复表达目录
--------------------

文件名应简洁但仍完整。

例如位于 Ecology/Environment/：

推荐：

7. 新核心：DB_FrameContext
======================================================================

每次 realized AI update 开始时，构造一个只描述“当前帧事实”的 context。

至少包括：

Identity:
- Creature；
- EntityID；
- Room；
- Tick / Frame；

Physical:
- Position；
- Velocity；
- Conscious；
- Dead；
- Restrained；
- InShortcut；
- InHive；
- Current Fly movement mode；
- Current FlyAI behavior；

Individual:
- Personality；
- PhysicalCapability；
- Injury severity；
- PostStunShock；
- Hydration / Thirst；
- Trauma；
- Grief；
- SocialBond summary；

Perception:
- nearest visible Player；
- current predator threat；
- validated thrown weapon observations；
- incoming projectile cue；
- room visibility factor；

Ecology:
- TravelIntent summary；
- SignalInfluence；
- EnvironmentInfluence；
- room flock snapshot；
- room shelter summary；

Rules:
- HardSurvival；
- CombatAllowed；
- SocialAllowed；
- CrossRoomOwned；
- SpecialPhysicsOwner。

DB_FrameContext 只用于当前帧/决策周期，不存档。

模块不得为了拿信息而 Reflection 另一个模块 private state。


======================================================================
8. 新核心：DB_BehaviorProposal / DB_BehaviorArbiter
======================================================================

8.1 Proposal contract
--------------------

每个行为模块可提交一个或多个 proposal。

建议字段：

DB_BehaviorProposal
- Owner；
- Priority；
- BehaviorKind；
- Goal；
- NominalSpeed；
- DesiredFlyBehavior（optional）；
- DesiredDijkstraMap（optional）；
- RequestBurrow；
- SuppressCombat；
- SuppressSocial；
- PreserveExistingGoal；
- ValidUntilTick / commitment；
- Reason；
- DebugSource。

Proposal 本身不得直接写 BodyChunk.vel。

8.2 Primary Owner priority
--------------------

推荐总体优先级保持现有批准语义：

1. Death / unconscious / destroyed；
2. Special physical restraint / grabbed / shortcut / emergence；
3. Immediate physical danger / escape；
4. Severe Injury / InjuryRecovery；
5. realized cross-room Travel；
6. Acute HardSurvival；
7. PTSD / direct threat reaction；
8. Extreme Vengeance；
9. Environment Preparation/Sheltering local survival；
10. projectile evade tactical modifier / immediate cue；
11. Formal Harass / Retaliation / Attack；
12. Roost / Chain；
13. Neutral Social Life；
14. ordinary DB idle/swarm behavior；
15. Vanilla FlyAI fallback。

注意：

- 具体数值可实现为 enum rank，不要求 magic int；
- Travel 有 intent 但当前因抓取/重伤 suspended 时，不应自动击败更高优先级；
- HardSurvival 可暂停 Vengeance，但不能清除 Vengeance memory；
- Signals 永远不应成为 locomotion owner；
- Threat Signature memory 本身永远不应成为 locomotion owner；
- visibility/navigation uncertainty 应作为 modifier，而不是第二 Primary Owner。

8.3 Arbiter result
--------------------

每帧只产生一个 DB_ResolvedBehavior：

- PrimaryOwner；
- WinningProposal；
- Modifiers；
- final Goal；
- final NominalSpeed；
- final Dijkstra ownership；
- final Combat/Social gates；
- reason；
- rejected proposals + reject reason（debug only）。


======================================================================
9. 新核心：DB_FlightMotor
======================================================================

DB_FlightMotor 是普通 Desert Batfly 飞行的唯一最终执行入口。

职责：

- 接受 Arbiter final goal；
- 设置 FlyAI.localGoal / native steering intent；
- 接受 nominal speed；
- 应用 Injury Forward/Turn/Lift/Acceleration modifier；
- 保持 native Fly collision / movement pipeline；
- 不实现第二套 path planner；
- 不 teleport；
- 不固定 Y；
- 不直接绕过 terrain collision。

Fog navigation error：

- 作为 goal modifier；
- 在 FlightMotor 前完成；
- 不自己写 velocity。

Injury：

- DB_InjuryRecovery 提交 recovery proposal；
- DB_InjuryFlightModifier 最终修改 native requested flight；
- 不在 InjuryRecovery 中持续独立写 vel。


======================================================================
10. 特殊物理所有权
======================================================================

以下行为允许明确绕过普通 DB_FlightMotor：

10.1 Emergence
- 可使用 MoveFromOutsideMyUpdate；
- 可临时关闭 collision；
- 结束时恢复 collision；
- 必须在 Cancel/Destroy/Room transition 恢复。

10.2 Attach / Interfere
- 可将 bat 约束到 target BodyChunk；
- 可同步目标 velocity；
- 可对目标施加批准的 drag/impulse；
- 必须有显式 enter/exit lifecycle；
- 退出后重新交还 DB_FlightMotor。

10.3 Hit / retaliation impulse
- 瞬时 impulse 允许直接写 velocity；
- 不得演变成多帧普通飞行控制器。

10.4 Native Burrow / Chain / Shortcut
- 原生 Rain World system 为物理 owner；
- Arbiter 只决定是否请求进入；
- 不替代原生执行。

11. 统一 DB_EventHub
======================================================================

必须建立统一事件入口，至少覆盖：

- DB_DamageEvent；
- DB_StunEvent；
- DB_CaptureEvent；
- DB_ReleaseEvent；
- DB_MortalityEvent；
- DB_ConsumeEvent；
- DB_RoomChangedEvent；
- DB_BurrowEvent；
- DB_EmergeEvent；
- DB_VengeanceArmedEvent；
- DB_DirectThreatObservedEvent；
- DB_AcuteEnvironmentEvent（若确实需要事件化）。

事件要求：

- 每个真实事件生成唯一 sequence/id；
- 单个事件对每个 subscriber 最多处理一次；
- 不依赖“90 tick 内相同对象就忽略”作为主要去重手段；
- 时间窗可继续用于语义归因，但不能替代 exactly-once dispatch；
- debug 可记录 event source 和 subscribers。

12. 统一死亡归因
======================================================================

新增 DB_MortalityEvent snapshot。

建议字段：

- Victim；
- Tick；
- Position；
- PrimaryCause；
- Instigator；
- SourceObject；
- DamageType；
- WasCaptured；
- WasConsumed；
- WasDirectAttack；
- WasProjectile；
- WasCounterKill；
- ThreatEvidence；
- DirectWitness snapshot；
- ChainWitness snapshot；
- ThreatScale；
- AttributionConfidence；
- DebugReason。

规则：

- live -> dead transition 只发布一次；
- Rocks 的“不能作为该次直接 finishing blow”规则保留；
- environmental death 可 Instigator=null；
- 被 Lizard 抓住后因其他 cause 死亡，不应自动把 Lizard 当 killer，除非统一 attribution 判断支持；
- Threat/Fear/Colony 不再各自重新猜 killer；
- 后续 Corpse Ecology 必须消费该事件，不再自行 Hook Death 做第二套归因。


======================================================================
13. 统一 DB_CaptureEvent
======================================================================

抓取检测与生态反应分离。

Detection：

- Player grasp；
- Peach tongue attach；
- Lizard bite/grasp；
- other supported lethal predator grasp。

Event consumer：

- Fear：capture fear；
- Signals：DistressCall / AlarmFlutter；
- Injury：capture shock/release survivor；
- Social：cancel neutral interaction；
- Threat：真实 capture evidence；
- Debug：一次事件追踪。

Peach integration 只负责检测 Watcher-specific tongue/bite transition，
不应再次独立完成全部 DB fear/social/signal side effects。


======================================================================
14. 统一 DB_RoomContext / Perception
======================================================================

目标：减少“一房间五套扫描器”。

14.1 Active bats cache
- 维护有效 realized DB_Creature list；
- dead/slated/inShortcut/inHive 可按不同 view 过滤；
- Social/Threat/Signals/Environment 不再各自完整枚举 colony list。

14.2 Players cache
- 当前 room player list；
- player slot；
- visibility query 仍按当前 bat 判断。

14.3 Weapon cache
- thrown weapons；
- owner/thrower；
- position/velocity；
- class/evidence type；
- low-frequency refresh + urgent direct event path。

使用者：
- ordinary weapon avoidance；
- Current Threat Cue；
- DenseFog close projectile recognition。

14.4 Predator candidates
- 只缓存候选，不缓存“这个 bat 一定害怕”；
- relationship/personality/range 仍由 individual decision 计算。

14.5 Roost / social candidates
- Social 可复用 ActiveBats / Roosting view；
- Reservation 仍由 Social 自己拥有。

14.6 Weather / shelter
- Environment 继续拥有天气与 shelter anchor；
- DB_RoomContext 只提供统一访问入口；
- 不把 Environment 数值语义搬进通用 perception。


======================================================================
15. Room Runtime 惰性与生命周期
======================================================================

15.1 激活

DB_RoomContext 不得对所有 realized rooms 自动做完整初始化。
昂贵数据仅在需要时创建。

15.2 清理

Room teardown / mod disable / game session reset 时必须：

- 释放 transient event queues；
- 清理 Room-scoped reservations；
- 清理 transient warning/effect registry；
- 清理 signal packets；
- 清理 environment room anchors/context；
- 不保留对 destroyed Room 的强引用。

ConditionalWeakTable 可继续使用，但不能把它当成“无需生命周期设计”的替代品。

15.3 Disable

DB_Hooks.Disable 后：

- 不允许 DB-owned UpdatableAndDeletable 继续影响生态逻辑；
- external hooks 必须卸载；
- static runtime state 必须清空；
- Warp/Sandbox compatibility 恢复外部状态；
- next Enable 不得出现重复 hook。

======================================================================
25. 性能目标
======================================================================

25.1 20～30 realized Desert Batflies

目标：在单房 20～30 只时不因本次架构增加明显 CPU spike。

25.2 禁止模式

- 每 bat 每 frame 完整扫描 room.physicalObjects；
- 每 bat 每 frame 完整扫描所有 Desert Batflies；
- 每 bat 每 frame terrain scan；
- Environment world graph scan；
- debug closed 时创建大量字符串；
- 多套重复 weapon scanner；
- 普通房间无 Desert Batfly 时创建完整 shelter anchor runtime。

25.3 推荐 cadence

- ActiveBats / players: 10～20 ticks 或事件驱动更新；
- thrown weapons: 8～12 ticks + urgent event；
- social candidates: 20 ticks；
- weather: 20 ticks；
- flock snapshot: 30 ticks；
- shelter anchors: build once / invalidate；
- crowding: 20 ticks；
- individual expensive decision: stagger 8～20 ticks；
- event delivery: event-driven bounded queue。

Cadence 可调，但必须保持分散刷新，避免所有 bat 同 tick 同时重算。

38. 最终代码心智模型
======================================================================

重构完成后，开发者看到一个 DB_ 文件名，应当能够立即知道它属于哪个职责。

理想运行流程：

    Rain World callback
          ↓
      DB_Hooks
          ↓
      DB_Runtime
          ↓
  DB_RoomContext / Perception
          ↓
     DB_FrameContext
          ↓
各领域模块提交 Influence / Event / BehaviorProposal
          ↓
  DB_BehaviorArbiter
          ↓
    PrimaryOwner
          ↓
     DB_FlightMotor
          ↓
  Rain World native Fly movement

事件流：

    External physical event
          ↓
      Adapter / Hook
          ↓
      DB_EventHub
          ↓
 Fear / Threat / Social / Signals / Colony / Debug

生产代码的领域心智模型应是：

- Core；
- Runtime；
- Perception；
- Combat；
- Injury；
- Vengeance；
- Social；
- Colony；
- Travel；
- Signals；
- Environment；
- Presentation；
- Integration；
- Debug。

而不是：

- Task09；
- Task10；
- Task11；
- Task12；
- Task13；
- 某某 Bridge；
- 某某 Patch；
- 某某兼容临时钩子。

39. 最终架构目标
======================================================================

重构完成后，新增一个 Desert Batfly 功能时，理想流程应是：

1. 新模块读取 DB_FrameContext / DB_RoomContext；
2. 若只是信息层，输出 influence/event；
3. 若需要移动，提交 DB_BehaviorProposal；
4. DB_BehaviorArbiter 决定是否获得当前帧所有权；
5. DB_FlightMotor/native FlyAI 执行；
6. 事件通过 DB_EventHub 发布；
7. Observatory 自动看到 owner、proposal、event；
8. 不需要为了接入旧模块再写 private Reflection/Detour/IL bridge；
9. 新文件使用 DB_ 前缀 + 完整职责名；
10. 不新增 TaskXX 运行时术语；
11. 不改变外部 "DesertBatfly" 身份和旧存档格式。

这才是本任务真正的成功标准。

本任务不是为了让文件“看起来短一点”，
也不是为了把 DesertBatfly 四个字机械替换成 DB_。

真正目标是让整个项目在继续扩展数十个生态功能后，仍然能够：

- 从文件名快速理解职责；
- 从目录快速定位领域；
- 明确谁拥有决策；
- 明确谁拥有移动；
- 明确事实从哪里产生；
- 明确谁可以修改什么状态；
- 明确哪些行为必须保持；
- 明确哪些名字属于外部兼容，哪些只是源码实现；
- 明确性能预算；
- 明确失败时在哪里调试。
