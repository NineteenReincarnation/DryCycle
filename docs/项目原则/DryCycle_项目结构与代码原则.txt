DryCycle 项目结构与代码原则
Project Structure, Architecture & Code Readability Principles

Revision: V1 / 2026-09-07
Scope: DryCycle 全项目
Status: 【长期工程原则 / 后续开发默认遵循】

======================================================================
0. 文档定位
======================================================================

本文件定义 DryCycle 后续长期开发所采用的项目结构、代码组织、依赖、命名、性能、测试与维护原则。

它不是某个具体 Task 的实现说明，也不规定某一功能必须使用某一种设计模式。

它的作用是：

1. 让项目在功能不断增加后仍然可读、可维护、可测试；
2. 避免历史 Task 编号、临时 Bridge、兼容补丁逐渐变成正式架构；
3. 避免为了“文件短”而机械拆分，也避免巨型文件无限吸收职责；
4. 让模块之间通过明确的数据、事件和接口协作，而不是依赖私有实现细节；
5. 让性能优化有统一方向，避免每个新系统都重新扫描同一份游戏状态；
6. 让重构、Bug 修复和后续扩展可以被安全回归验证。

除非具体任务书明确说明例外，后续新代码和大规模重构默认遵循本文件。


======================================================================
1. 第一原则：架构服务于职责，不服务于形式
======================================================================

目录、文件、类、接口、Runtime 的划分首先回答：

“这段代码负责什么？”

而不是：

“这个文件有多少行？”
“这个 Task 当年编号是多少？”
“为了看起来整齐是不是应该再套一层目录？”

项目结构的目标是降低理解和修改成本，而不是追求视觉上的绝对对称。

允许两个领域拥有不同的内部结构，只要：

- 职责清楚；
- 依赖方向明确；
- 生命周期明确；
- 测试边界明确；
- 不产生不必要耦合。


======================================================================
2. Domain First / 领域优先
======================================================================

大型功能优先按领域组织，而不是按开发历史组织。

推荐领域名称示例：

- Weather
- Travel
- Colony
- Signals
- Threat
- Social
- Combat
- Injury
- Environment
- Graphics
- Hydration
- WorldLink

禁止把生产代码长期组织成：

- Task09/
- Task10/
- Task13/
- Phase2/
- NewSystem/
- Temp/
- OldVersion/

Task 编号属于需求与开发历史，不属于运行时领域模型。


======================================================================
3. Single Responsibility 不是“一类只能做一件小事”
======================================================================

单一职责应理解为：

“一个模块应围绕一个稳定的修改理由变化。”

例如一个完整的 WorldRoutePlanner 可以包含：

- 图搜索；
- cost evaluation；
- route reconstruction；
- route validation；
- route commitment；

只要这些内容始终围绕“世界路线规划”一起变化，就可以保持在同一个高度内聚模块中。

反之，一个只有数百行的文件如果同时承担：

- 扫描玩家；
- 扫描武器；
- 判断天气；
- 选择攻击；
- 写移动；
- 发信号；
- 训练记忆；
- 写 Debug；

即使文件不长，也应视为职责过载。


======================================================================
4. 文件大小：只作为 Review Trigger，不作为硬限制
======================================================================

DryCycle 不设置生产源码的强制最大行数。

不得使用：

- 500 行必须拆；
- 800 行必须拆；
- 1200 行禁止存在；

这类机械规则作为验收条件。

文件明显增大时，只触发“职责审查”。

建议在较大的手写生产文件（例如约 800～1200 行及以上）出现时主动检查，但数字本身不决定是否拆分。

真正的拆分依据是：

1. 是否存在多个独立修改理由；
2. 是否存在低内聚的独立子领域；
3. 是否有部分代码可以独立测试和演化；
4. 是否有部分代码被其他模块单独使用；
5. 理解一个功能时是否必须阅读大量无关逻辑；
6. 文件是否频繁成为多个功能改动的共同冲突点；
7. 是否暴露过大的 public/internal API surface；
8. 是否出现明显不同的生命周期或状态所有权。

判断建议：

- 0～1 项明显成立：通常无需因为文件大而拆；
- 2～3 项成立：应认真评估拆分；
- 4 项以上成立：通常说明职责边界已经需要调整。

文件长度是 Code Smell / Review Signal，不是 Architecture Rule。


======================================================================
5. 禁止机械碎片化
======================================================================

为了缩短文件而产生大量无意义碎片，同样属于低质量结构。

禁止典型命名：

- Part1 / Part2 / Part3
- HelperA / HelperB
- Utils2
- Manager1
- MiscLogic
- CommonStuff

一个复杂但高度内聚的状态机、解析器、路线规划器或协议实现，可以合理地保持为较大文件。

拆分后每个新文件必须有可解释的领域职责，而不是仅仅承担“原文件的一部分行数”。


======================================================================
6. 目录深度：优先可导航，不追求层级完美
======================================================================

目录应帮助开发者快速定位领域。

不建议为了理论分层形成过深路径，例如：

    Behavior/Social/Runtime/States/Internal/...

当一个子系统已经是完整领域时，可以直接作为一级或二级领域目录。

例如一个复杂生物模块可以采用：

    Core/
    Runtime/
    Combat/
    Injury/
    Social/
    Threat/
    Signals/
    Environment/
    Colony/
    Travel/
    Presentation/
    Integration/
    Debug/

而不必把所有领域强行塞进 Behavior/ 或 Ecology/ 再多套一层。

原则：

- 常用领域应尽量 2～3 次点击内可达；
- 目录名称直接表达业务职责；
- 不为只有一个小文件的概念提前建立多层空目录；
- 当领域成长后再自然拆分。


======================================================================
7. 避免泛化垃圾目录
======================================================================

除非确实是全项目共享基础设施，否则不推荐新建：

- Utils/
- Helpers/
- Misc/
- Managers/
- Common/

如果 helper 只服务 Travel，它应属于 Travel。
如果 formatter 只服务 Observatory，它应属于 Debug/Observatory。
如果算法只服务 Signals，它应属于 Signals。

真正跨领域的设施应有明确的基础职责，例如：

- Runtime
- Perception
- Events
- Serialization
- Integration

而不是因为“不知道放哪”就放 Utils。


======================================================================
8. 命名：短前缀 + 完整职责
======================================================================

一个大型子系统可以定义短且稳定的源码前缀，以降低文件名同质化和 IDE 搜索噪音。

例如 Desert Batfly 采用：

    DB_

推荐：

- DB_Runtime
- DB_TravelIntent
- DB_ThreatMemory
- DB_EnvironmentRuntime
- DB_SignalDefinition

不推荐二次压缩：

- DB_EnvRt
- DB_TrvInt
- DB_BhvMgr
- DB_T13

原则：

“前缀短，职责名完整。”

其他复杂子系统是否采用前缀，应由该领域任务书决定，不要求整个 DryCycle 所有类型都带前缀。


======================================================================
9. 开发历史名称不得污染生产架构
======================================================================

Task、Phase、讨论编号只用于：

- docs/Task；
- docs/Discussion；
- Git history；
- 重构迁移期临时测试标识。

生产代码应使用领域名称。

例如：

    Task13Influence          -> EnvironmentInfluence
    Task09Travel             -> TravelIntent
    Task12SignalBridge       -> SignalRuntime / SignalPolicy

历史编号不能成为永久 API。


======================================================================
10. 源码名称与外部身份必须分离
======================================================================

内部 C# 重命名不应轻易改变游戏、资源、存档或第三方可见 ID。

例如：

    DesertBatflyState -> DB_State

不意味着：

    "DesertBatfly" Creature ID 必须改名
    DCDesertBatflyV1 save tag 必须改名

以下内容默认视为兼容边界：

- CreatureTemplate.Type / ExtEnum 字符串；
- Sandbox unlock ID；
- save tag/schema；
- world.txt / room / object tag；
- atlas / shader / asset key；
- JSON config key；
- 第三方 Mod 依赖的外部名称。

外部 ID 只有在明确安排迁移策略、兼容层和回归测试后才能修改。


======================================================================
11. Cohesion / 内聚优先
======================================================================

同一模块内部的状态、算法和生命周期应高度相关。

一个模块如果必须同时理解多个不相关领域才能修改其中一个行为，说明内聚不足。

重构时优先把：

- 一起变化；
- 一起测试；
- 一起拥有状态；
- 一起清理生命周期；

的代码留在一起。

不要仅按“数据类 / service 类 / manager 类”机械拆分。


======================================================================
12. Change Coupling / 关注一起变化的文件
======================================================================

如果一个简单参数修改经常必须同时修改多个不相关模块，说明边界存在重复 authority 或隐式耦合。

例如 Signal visual range 应有唯一 authority。

正确：

    SignalDefinition.VisualRange
        -> SignalRuntime 读取
        -> Fog/VisibilityPolicy 只提供 multiplier

不正确：

    Signals 复制一份 range
    Environment 再复制一份
    Debug 再复制一份

原则：

“一个领域事实尽量只有一个 authoritative definition。”


======================================================================
13. Explicit Dependencies / 依赖必须显式
======================================================================

模块不应通过：

- Reflection 读取兄弟模块 private field；
- RuntimeDetour 挂兄弟模块 private method；
- 字符串方法名；
- 临时修改另一个系统的持久状态；
- 读取未声明的全局 static；

来形成内部协议。

内部跨模块协作优先使用：

- 明确数据结构；
- Context；
- Event；
- Policy；
- readonly state view；
- Proposal / Result；
- 显式 internal API。

Reflection / Harmony / RuntimeDetour 应主要存在于真正的游戏/第三方 Integration 边界。


======================================================================
14. 依赖方向应尽量单向
======================================================================

避免多个领域互相直接调用形成环：

    Combat <-> Social <-> Environment <-> Threat <-> Signals

更健康的形式是通过稳定中间契约：

    Room/Frame Context
    Event Hub
    Proposal/Arbiter
    Read-only Influence

例如：

- Environment 输出 EnvironmentInfluence；
- Combat 读取影响，而不是 Environment detour Combat 私有方法；
- Signals 输出 SignalInfluence；
- Social 读取影响，而不是 Signals 直接改 Social private state。


======================================================================
15. 状态必须有明确 Owner
======================================================================

每一个重要状态都应回答：

- 谁创建？
- 谁修改？
- 谁读取？
- 是否持久化？
- 何时清理？
- Room change / death / disable 后是否还存在？

禁止多个模块都把同一字段当作自己的临时通信通道。

例如持久 Thirst 不能被 Environment 临时篡改来表达 HeatAgitation。

应建立明确的 decision/motivation context。


======================================================================
16. 行为所有权：同一物理结果只能有一个主控制器
======================================================================

对于移动、Camera、Weather state 等容易产生控制冲突的领域，应明确“当前 owner”。

特别是生物普通 locomotion：

- 同一帧只允许一个 Primary Movement Owner；
- 其他系统提交 influence / proposal / modifier；
- 不能多个系统持续直接写速度或目标互相覆盖。

特殊物理状态可显式取得所有权，例如：

- 抓附；
- 被抓；
- shortcut；
- emergence；
- 瞬时 hit impulse。

关键不是“任何地方都禁止写 velocity”，而是普通行为不能形成多套并行 locomotion controller。


======================================================================
17. Event Semantics / 真实事件只解释一次
======================================================================

同一个游戏事实不应被多个 Hook 独立重新解释。

典型事件：

- Damage
- Capture
- Release
- Death
- Consume
- RoomChanged
- Weather transition

推荐流程：

    外部 Hook / Detector
        -> 统一 semantic event
        -> 多个 subscriber 消费同一事实

而不是：

    Hook A 猜一次 killer
    Hook B 再猜一次 killer
    Hook C 根据 grabbedBy 第三次猜

事件应尽量 exactly-once，并拥有 sequence/tick/source 信息。

时间窗可以用于语义归因，但不能替代 event 去重设计。


======================================================================
18. Runtime 生命周期必须显式
======================================================================

使用 ConditionalWeakTable 不等于无需设计生命周期。

所有 Room / Creature / Session scoped runtime 都应考虑：

- Enable；
- Disable；
- Reset；
- Room transition；
- Creature death；
- shortcut；
- game/session teardown；
- mod reload（可支持范围内）。

如果创建 UpdatableAndDeletable / Hook / reservation / static registry，必须有对应清理路径。


======================================================================
19. Room Runtime 应按需激活
======================================================================

昂贵 Room 分析不应仅因为 Room.Update 就在所有房间启动。

例如：

- terrain shelter scan；
- creature ecology cache；
- signal packet runtime；
- specialized AI context；

应优先在真实需要时建立。

典型激活条件：

- 相关生物/对象存在；
- 相关系统明确查询；
- 相关区域配置存在；
- Debug 明确请求。


======================================================================
20. 性能原则：共享观察，避免重复扫描
======================================================================

当多个系统依赖同一 Room 事实时，应考虑共享低频 observation/cache。

例如：

- players；
- thrown weapons；
- active creatures；
- weather；
- shelter geometry；
- roost candidates。

禁止模式：

- 每只生物每帧完整扫描 physicalObjects；
- 每个子系统各自重复扫描同一 thrown weapon list；
- 每帧 terrain full scan；
- Debug 关闭时仍持续构造大量字符串。

优化目标不是“缓存一切”，而是消除明显重复工作并保持 cache freshness 可解释。


======================================================================
21. 性能预算应按算法与频率描述
======================================================================

比“文件多少行”更值得设置硬指标的是运行复杂度。

应明确：

- 是否 per-frame；
- 是否 per-creature；
- 是否 room-wide；
- 是否 world-wide；
- 最大集合规模；
- refresh cadence；
- cache invalidation；
- 上限/cap。

推荐优先设置：

- packet cap；
- relay hop cap；
- route max hop；
- candidate limit；
- refresh interval；
- per-frame owner count；

而不是设置无业务意义的源码行数上限。


======================================================================
22. API Surface 越小越容易维护
======================================================================

模块对外应尽量暴露稳定的领域接口，而隐藏内部实现。

例如 Signals 外部更适合看到：

- Publish
- Update
- GetInfluence
- Definition

而不是直接访问：

- generation ring；
- merge buffer；
- urgent queue；
- receiver dictionary。

公开/跨模块 internal API 增加时应问：

“调用者真的需要知道这个实现细节吗？”


======================================================================
23. 方法结构优先显式阶段
======================================================================

复杂逻辑优先组织成：

- Gather / Sample
- Evaluate
- Build
- Resolve
- Apply
- Publish
- Cleanup

等可理解阶段。

一个方法同时：

扫描全房间 + 选择目标 + 修改持久状态 + 写移动 + 发事件 + 写 Debug

即使只有几百行，也应视为重构候选。


======================================================================
24. 注释解释“为什么”，代码表达“做什么”
======================================================================

推荐注释记录：

- 为什么某个优先级必须高于另一个；
- 为什么不能读取某个输入；
- 为什么保留某个旧外部 ID；
- 为什么某个算法没有换成更复杂方案；
- 特殊兼容边界；
- 不直观的 Rain World 原版语义。

不推荐大量重复代码本身已经清楚表达的内容。


======================================================================
25. 不为“高级架构”而过度抽象
======================================================================

DryCycle 是 Rain World Mod，不需要照搬企业后端的所有模式。

禁止为了架构形式引入：

- 无实际替换需求的接口层层包装；
- 每个类都配 Factory；
- 所有逻辑都 Event Bus 化；
- 只有一个实现却增加多层 Repository/Service；
- 为了“解耦”制造几十个只转发一次调用的 Adapter。

抽象必须解决真实问题：

- ownership；
- testability；
- duplicate observation；
- external integration；
- lifecycle；
- future extension pressure。


======================================================================
26. 保留 Rain World 原生能力，避免不必要重造
======================================================================

如果 Rain World 已经提供稳定能力，优先复用：

- native pathing；
- collision；
- shortcut；
- creature relationship；
- chain/roost；
- abstract movement；

只有原生能力确实不满足设计目标时才建立新的实现。

重构不应为了“代码更现代”替换已经稳定工作的底层算法。


======================================================================
27. Compatibility 与 Core 分离
======================================================================

外部 Hook、Reflection、Harmony、Watcher/Warp 兼容应尽可能集中到：

- Integration；
- Compatibility；
- Adapter；

Core/Domain 不应依赖某个第三方 Mod 的私有字段才能正常运行。

兼容层失败应尽量 fail soft，并可通过 Debug 明确记录。


======================================================================
28. Persistence / 存档稳定性优先
======================================================================

重构生产类型名不等于重写存档格式。

修改持久 schema 前必须考虑：

- old save load；
- malformed data；
- locale；
- unknown/foreign fields；
- migration path；
- rollback。

如果没有明确玩法需求，架构重构默认不改变已有 save schema。


======================================================================
29. 测试保护行为契约，不保护历史技术债
======================================================================

测试应该验证：

- 行为结果；
- priority；
- ownership；
- event exactly-once；
- persistence；
- bounded math；
- forbidden side effect；
- dependency boundary。

不应该长期验证：

- 某个 xxxBridge 必须存在；
- 某个 private Hook 必须存在；
- 某个 RuntimeDetour 必须被调用；
- 某方法必须在 IL offset 上排在另一个方法之前。

迁移阶段可暂时保留 Architecture Lock Test，但最终应转化为 Behavior/Contract Test。


======================================================================
30. Debug / Observatory 应读取真实状态
======================================================================

Debug 不应根据多个状态变量“猜”当前 owner，如果 runtime 本身已经有明确 owner。

应优先暴露：

- current owner；
- winning decision；
- rejected proposals；
- event source；
- cache age；
- current context；
- lifecycle state。

Debug 应帮助定位架构冲突，而不只是展示结果数值。


======================================================================
31. 提交纪律
======================================================================

大规模重构应避免一次提交同时进行：

- 大量文件移动；
- 大量 rename；
- 行为逻辑变化；
- API 改写；
- 测试删除。

推荐拆分：

1. baseline regression；
2. 新 contract/API；
3. 单一子系统迁移；
4. 删除旧 bridge；
5. 文件 rename/move；
6. cleanup；
7. performance/tuning。

目标是让 Git diff 可审查、Bug 可 bisect、阶段可回滚。


======================================================================
32. 重构优先保持行为
======================================================================

架构重构默认采用 Behavior-Preserving Refactor。

除非任务书明确批准，不应借机：

- 改玩法；
- 改概率；
- 改 Personality 分布；
- 改存档；
- 加新机制；
- 删除玩家已依赖的行为。

Bug 修复应单独记录并有回归依据。


======================================================================
33. 新增系统前的 Architecture Check
======================================================================

增加一个较大新功能前，先回答：

1. 它属于哪个领域？
2. 它拥有自己的状态吗？
3. 状态是 persistent、session、room 还是 frame？
4. 它需要读取哪些已有事实？
5. 是否已有可复用 Context / Event / Perception？
6. 它是否需要成为行为/移动 owner？
7. 如果需要，如何进入已有 arbitration？
8. 它是否会重复扫描已有数据？
9. 生命周期如何清理？
10. 如何测试？

如果新功能必须先写多个 private Reflection Bridge 才能接入，通常说明旧架构需要先扩展正式 contract。


======================================================================
34. 文件拆分“五问法”
======================================================================

准备拆一个文件前优先问：

Q1. 是否有多个独立修改理由？
Q2. 是否有可独立测试的子职责？
Q3. 是否有被其他模块单独消费的子职责？
Q4. 修改一个功能时是否必须阅读大量无关代码？
Q5. 是否频繁成为不同功能修改的共同冲突点？

拆分必须能明确回答：

“拆完后，每个文件分别代表哪个稳定领域职责？”

如果无法回答，只是因为文件行数大，则先不要机械拆。


======================================================================
35. 项目结构 Review 的优先级
======================================================================

评审代码结构时，优先顺序建议为：

1. Correctness / 行为正确；
2. Ownership / 谁负责；
3. Lifecycle / 何时创建和销毁；
4. Dependency / 依赖是否明确；
5. Cohesion / 是否高度内聚；
6. Performance / 是否存在重复昂贵工作；
7. Testability / 是否能稳定验证；
8. Readability / 是否容易导航理解；
9. File size / 文件长度提醒。

文件行数应位于较低优先级，不应覆盖前面的架构判断。


======================================================================
36. 允许例外，但必须有理由
======================================================================

本文件不是为了禁止工程判断。

如果某个模块合理地违反一般建议，例如：

- 一个高度内聚状态机超过 1200 行；
- 一个外部兼容文件必须使用 Reflection；
- 某个性能路径必须直接操作原生对象；

可以保留，但应满足：

1. 责任清楚；
2. 理由可记录；
3. 边界可测试；
4. 不把例外扩散成全项目默认方式。


======================================================================
37. 文档组织
======================================================================

当前 docs 允许三个一级目录：

    docs/
    ├─ Task/
    ├─ Discussion/
    └─ 项目原则/

Task：正式任务书与可执行规格。
Discussion：讨论、设计过程、状态和历史记录。
项目原则：跨任务、跨模块长期复用的工程规范。

具体功能的规则优先写进对应 Task；
只有真正能够长期复用的规则才进入“项目原则”。


======================================================================
38. 最终目标
======================================================================

DryCycle 项目结构的成功标准不是：

- 文件都很短；
- 目录完全对称；
- 使用了很多设计模式；
- 所有东西都有接口。

真正目标是：

- 开发者能快速找到一个行为属于哪里；
- 修改一个领域时不需要理解大量无关系统；
- 同一个事实只有清晰 authority；
- 同一个状态有明确 owner；
- 同一个物理行为不会被多套控制器竞争；
- 外部兼容和核心逻辑分离；
- 性能成本有界；
- 生命周期能够正确清理；
- 测试保护行为而不是保护历史补丁；
- 项目继续增加大量功能后仍然能安全扩展。
